# Enforcement & Reliability

*Guaranteed vs. suggested behavior — hooks vs. prompts, programmatic gates, escalation-trigger design, stop_reason handling, human-review gates, and how much autonomy is actually safe.*

## The thread

The field's builders converge on one hard line: **anything that must be guaranteed cannot live in a prompt.** Prompts, CLAUDE.md, and system instructions are *advisory* — the model can and will ignore parts of them, especially as context fills and earlier instructions decay ([blog-claude-code-best-practices](../research/notes/blog-claude-code-best-practices.md)). Hooks, schema validation, prerequisite gates, and exit-code checks are *deterministic* — they run whether or not the model "wants" to. So the design question is never "how do I word this so Claude complies?" It is "is this a guarantee or a preference?" Guarantees get code; preferences get heuristics. This is the single most-tested CCA-F concept and the root of anti-pattern #3 (prompt-based enforcement of critical rules).

The second load-bearing idea is that **reliability compounds multiplicatively, not additively.** Long-horizon agent failures bottleneck on "nines of reliability," and chaining steps multiplies the failure probability — a 95%-reliable step run ten times succeeds end-to-end only ~60% of the time ([dwarkesh-sholto-trenton](../research/notes/dwarkesh-sholto-trenton.md)). In long-running stateful systems "a small failure early can send the whole trajectory off course" ([blog-multi-agent-research](../research/notes/blog-multi-agent-research.md)). This is why verification gates between steps matter more than a better final prompt, and why resumable checkpoints beat restart-from-zero.

The third idea reframes autonomy: **you earn the right to remove the human by making the work self-verifiable.** Sid Bidasaria's "Stop babysitting your agents" is the crisp version — give Claude a way to verify its own work in a loop (write code, run it, open the browser, check the result, fix, repeat) so the human stays out of the loop *until the work is actually done* ([cwc-stop-babysitting](../research/notes/../transcripts/cwc-stop-babysitting.md)). The two domains with proven full-autonomy PMF — coding assistants and deep research — are exactly the two where the agent can check itself (tests/compiler; search-and-synthesize) ([stytch-agent-ready-ep8](../research/notes/stytch-agent-ready-ep8.md)). Where the action isn't self-verifiable (moving money, regulated decisions), autonomy is not safe and a human/programmatic gate stays in. See [evals](evals.md) for how self-verification gets measured.

## Patterns

**Hooks over prompts (programmatic enforcement).** A hook is a script that fires at a defined point and is guaranteed to run; a CLAUDE.md line is a suggestion. Use hooks for anything that must always happen: format-on-save, blocking commits without tests, prerequisite gates before a tool fires. ([blog-claude-code-best-practices](../research/notes/blog-claude-code-best-practices.md))

**Verification gates.** Between steps, demand a pass/fail signal — tests, build exit code, linter, diff fixture, screenshot comparison. Without one, "'looks done' is the only signal, and the human becomes the verification loop." Ask Claude to *show evidence*, not assert success. ([blog-claude-code-best-practices](../research/notes/blog-claude-code-best-practices.md)) Evals generalize this: grade the *outcome*, not the exact path ([blog-demystifying-evals](../research/notes/blog-demystifying-evals.md), [blog-multi-agent-research](../research/notes/blog-multi-agent-research.md)).

**Escalation-trigger design.** Escalate on *structural* conditions, never on the model's feelings. Three valid triggers: explicit customer request for a human, policy gap (no rule covers the case), capability limit (AI literally can't do the action). Two invalid traps: sentiment ("customer sounds angry") and self-reported confidence ("I'm 60% sure"). Both are model-generated signals with no ground truth. (Project CLAUDE.md; anti-patterns #4–5)

**stop_reason as loop control.** Terminate the agent loop by checking the API's `stop_reason` field (`end_turn`, `tool_use`, `max_tokens`), never by parsing the model's natural-language output for "I'm done." An iteration cap is a *safety net*, not the primary stopping mechanism. (Project CLAUDE.md; anti-patterns #1–2)

**Human-in-the-loop for high-stakes.** For regulated/opaque domains (customer support, payments), hybrid human-in-loop beats end-to-end autonomy because the end user lacks visibility into what the agent did ([stytch-agent-ready-ep8](../research/notes/stytch-agent-ready-ep8.md)). Autonomous agents ship only with "extensive sandbox testing, guardrails, and human checkpoints" ([blog-building-effective-agents](../research/notes/blog-building-effective-agents.md)).

**Fresh-context / separate-session review.** Same-session self-review invites confirmation bias (anti-pattern #9). A parallel session reviewing code it didn't write catches more ([blog-claude-code-best-practices](../research/notes/blog-claude-code-best-practices.md)); generation and evaluation belong in separate sessions ([blog-demystifying-evals](../research/notes/blog-demystifying-evals.md)).

**Poka-yoke (error-prevention by design).** Make error classes impossible rather than instructing against them: requiring absolute file paths eliminated an entire class of working-directory bugs ([blog-building-effective-agents](../research/notes/blog-building-effective-agents.md)). Related in [tool-design-and-mcp](tool-design-and-mcp.md).

**Self-recovery loop (the agent verifies itself).** Production long-running agents must detect when output diverges from the expected outcome and revise course *without* human steering — "self-recovery is non-negotiable." The design shift is from prescribing an exact output structure to specifying a desired *outcome/metric* and letting the agent iterate to it (outcome optimization). This is the harness doing the enforcement: the scaffolding around the model — not the model alone — is "what elevates us from random token sampling to actual actionable products" ([behind-craft-jess-yan](../research/notes/behind-craft-jess-yan.md)). See [orchestration-patterns](orchestration-patterns.md).

**Character as the enforcement layer for un-specifiable judgment.** Rules and hooks cover behaviors you can pre-specify. The residue — judgment calls an unsupervised long-horizon agent makes that no rule anticipated — is governed by the model's *character* (its beliefs and values). Alex Albert: when an agent runs unsupervised, "the questions of what its character is and what it cares about are very important," because character determines decision quality where no gate exists. So character is not decoration; for the un-specifiable slice it is the reliability mechanism, evaluated as a hybrid (quantitative — how often does it push back? — plus qualitative transcript reading) ([behind-craft-alex-albert](../research/notes/behind-craft-alex-albert.md)).

## Numbers & rules of thumb

- **8 consecutive blocks** — a Stop hook is overridden by Claude Code after 8 blocks; a hard-coded safety escape hatch so hooks can't trap the agent forever. ([blog-claude-code-best-practices](../research/notes/blog-claude-code-best-practices.md))
- **2 failed corrections** — after two failed fixes on the same issue, `/clear` and rewrite beats continued patching. ([blog-claude-code-best-practices](../research/notes/blog-claude-code-best-practices.md))
- **pass@k vs. pass^k** — customer-facing agents need pass^k (succeeds *every* time; 75% single-trial → 0.75³ ≈ 42% over 3); research can accept pass@k (≥1 success in k). Mismatched metrics hide instability. ([blog-demystifying-evals](../research/notes/blog-demystifying-evals.md))
- **0% pass rate** across many trials usually means a broken task/grader, not an incapable model. ([blog-demystifying-evals](../research/notes/blog-demystifying-evals.md))
- **>5 tools** per agent degrades selection reliability; 18+ tools is a known failure mode. (anti-pattern #8)
- **~0.5 reliability elasticity of chaining** — each added step multiplies failure; design for "9s" early, not post-hoc. ([dwarkesh-sholto-trenton](../research/notes/dwarkesh-sholto-trenton.md))
- **3 approval-fatigue reducers** — auto mode (classifier gates risky actions), permission allowlists, OS-level sandboxing. Headless runs scope with `--allowedTools`. ([blog-claude-code-best-practices](../research/notes/blog-claude-code-best-practices.md))
- **Two proven full-autonomy domains** — coding + deep research (both self-verifiable). ([stytch-agent-ready-ep8](../research/notes/stytch-agent-ready-ep8.md))

## Where speakers disagree

**"Flexible heuristics" vs. "brittle if/then."** The context-engineering team argues system prompts should express behavior as *flexible heuristics*, not rigid if/then logic ([blog-context-engineering](../research/notes/blog-context-engineering.md)) — which sounds like the opposite of the enforcement thread's "encode the rule in code." The resolution: they operate on different layers. Guidance *to the model* about judgment calls should be flexible (rigid prompt logic is brittle and gets ignored). Guarantees *of the system* about must-never-happen actions belong in deterministic code. Heuristics for what the model decides; hooks for what must be true regardless.

**How durable is human oversight?** Sholto/Trenton expect near-term systems built from multiple smaller models talking in natural language *specifically to preserve human oversight* ([dwarkesh-sholto-trenton](../research/notes/dwarkesh-sholto-trenton.md)). Cal Rueb counters that sub-agents are "a short-term workaround for today's limited context windows," likely unnecessary as capacity grows ([stytch-agent-ready-ep8](../research/notes/stytch-agent-ready-ep8.md)). One treats the inspectable multi-agent split as a safety feature; the other as a temporary scaffold. Cherny's framing — scaffolding buys only 10–20% and decays ([yc-inside-claude-code](../research/notes/yc-inside-claude-code.md)) — leans toward the scaffold view.

**Reduce babysitting vs. keep humans in high-stakes loops.** Bidasaria's whole talk is about *removing* the human ([cwc-stop-babysitting](../research/notes/../transcripts/cwc-stop-babysitting.md)); the stytch panel and building-effective-agents insist on human checkpoints for regulated work. Not a real contradiction — the reconciling variable is verifiability. Remove the human where the agent can check itself; keep the gate where it can't.

**Permanent gates vs. progressive safety scaling.** The enforcement thread says guarantees live in deterministic code, full stop. Cherny pushes a temporal caveat: as model alignment improves, safety *harnesses* (prompt-injection guards, static verification, some permission prompts) become *less* critical, and you should migrate enforcement code → prompts → native model behavior rather than build permanent scaffolding — "don't over-engineer permanent safety scaffolding for today's model limitations" ([cherny-sequoia-ascent](../research/notes/cherny-sequoia-ascent.md)). This is not a licence to put business-critical guarantees in prompts — the guarantee/preference line holds for irreversible actions (money movement still gets a gate). What decays is the *defensive* scaffolding that only ever bought ~10–20% and offset model weakness; as the weakness closes, the scaffolding is dead weight. Read it as: gate the irreversible forever, but let capability-compensating scaffolding sunset on a 3–12 month clock.

## Interview-ready takes

1. **"If it must be guaranteed, it goes in code, not a prompt."** Hooks/schema/gates are deterministic; CLAUDE.md is advisory and decays as context fills. This is the first question to ask of any requirement: guarantee or preference? ([blog-claude-code-best-practices](../research/notes/blog-claude-code-best-practices.md))

2. **"Autonomy is earned through verifiability, not granted by prompt."** The safe autonomy level equals how well the agent can check its own work. Coding and research are self-verifiable, so they hit full autonomy first; money movement isn't, so it keeps a gate. ([cwc-stop-babysitting](../research/notes/../transcripts/cwc-stop-babysitting.md), [stytch-agent-ready-ep8](../research/notes/stytch-agent-ready-ep8.md))

3. **"Escalate on structure, terminate on stop_reason."** Valid escalation triggers are structural (customer request, policy gap, capability limit); sentiment and confidence scores are traps. Loop termination reads `stop_reason`; iteration caps are only a safety net. (Project CLAUDE.md)

4. **"Reliability compounds — put gates between steps, not just at the end."** A 95% step chained ten times is ~60% end-to-end; verification gates and resumable checkpoints stop early errors from cascading. ([dwarkesh-sholto-trenton](../research/notes/dwarkesh-sholto-trenton.md), [blog-multi-agent-research](../research/notes/blog-multi-agent-research.md))

5. **"Match the metric to the stakes: pass^k for customers, pass@k for research."** Reporting aggregate accuracy hides the instability that matters for a customer-facing agent that must succeed every single time. ([blog-demystifying-evals](../research/notes/blog-demystifying-evals.md))
