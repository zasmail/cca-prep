# Orchestration Patterns

## The thread

Anthropic's builders converge on one blunt claim: **most "agent" projects should not be agents at all.** The dominant advice is to start with a single augmented LLM call plus retrieval and few-shot examples, then climb a ladder of complexity only when each rung earns its keep — single-shot → agent loop → workflows of chained agents → multi-agent orchestration ([blog-building-effective-agents](../research/notes/blog-building-effective-agents.md), [building-more-effective-agents](../research/notes/building-more-effective-agents.md)). The distinction that organizes everything is **workflow vs. agent**: workflows run LLMs and tools through predefined code paths; agents let the model itself direct its process and tool use. Workflows fit predictable, well-scoped tasks; agents fit open-ended problems where you cannot hardcode the number or shape of steps. Autonomy is not free — it trades latency, cost, and compounding-error risk for flexibility.

The canonical taxonomy is the **five patterns** from "Building Effective Agents": prompt chaining, routing, parallelization, orchestrator-workers, and evaluator-optimizer. These are composable building blocks to remix, not a rigid hierarchy. Anthropic repeatedly warns against heavyweight frameworks that add abstraction layers obscuring what's actually happening; most patterns are a few lines of direct API code ([blog-building-effective-agents](../research/notes/blog-building-effective-agents.md)).

Multi-agent is the top of the ladder and the most expensive rung. Anthropic's research system — the reference implementation of orchestrator-workers — beat a single agent by **90.2%** on internal research evals but costs **~15x the tokens** of a normal chat ([blog-multi-agent-research](../research/notes/blog-multi-agent-research.md)). That economics is the whole decision: multi-agent only pays off for high-value tasks whose subproblems parallelize with loose coupling. It is a poor fit for tightly-interdependent work like most coding, where shared context matters more than parallel surface area.

A parallel current pushes the other direction. As models improve, the required scaffolding *shrinks* — "unhobbling" the model by giving it tools and autonomy beats constraining it ([building-future-of-agents](../research/notes/building-future-of-agents.md)). And a newer school argues the real leverage isn't more orchestration at all but **skills** — packaged procedural knowledge loaded via progressive disclosure — so that a general code-execution loop plus a skill library replaces bespoke multi-agent scaffolds ([dont-build-agents-build-skills](../research/notes/dont-build-agents-build-skills.md)). See [skills-and-progressive-disclosure](skills-and-progressive-disclosure.md).

## Patterns

**Prompt chaining** — Decompose a task into ordered LLM steps, each feeding the next, with **programmatic validation gates between steps**. Trades latency for higher per-step accuracy. Use when a task cleanly splits into fixed subtasks and you want to gate on quality before proceeding (draft→translate; outline→write with a check in between). [blog-building-effective-agents](../research/notes/blog-building-effective-agents.md)

**Routing** — Classify the input, then dispatch to a specialized handler so each category gets its own optimized prompt/model. Use when inputs fall into distinct classes that a single prompt handles poorly, or to route easy queries to a cheaper model (Haiku) and hard ones to a stronger one (Sonnet). Force the classification with `tool_choice`. [blog-building-effective-agents](../research/notes/blog-building-effective-agents.md)

**Parallelization** — Two variants: *sectioning* (split into independent subtasks run concurrently) and *voting* (run the same task multiple times for consensus/diverse takes). Use for latency reduction on independent work or higher confidence via multiple perspectives (one path answers while another screens for policy violations). [blog-building-effective-agents](../research/notes/blog-building-effective-agents.md)

**Orchestrator-workers** — A central LLM breaks the task into subtasks *dynamically per input*, dispatches to workers, and synthesizes results. The distinction from static parallelization: the breakdown is decided at runtime, not fixed in advance. The **coordinator manages ALL inter-agent communication — workers never talk to each other directly.** Canonical example: the multi-agent research system (LeadResearcher spawns parallel Subagents, then a CitationAgent attaches sources). Best for decomposable research/discovery; poor for tightly-coupled reasoning. [blog-multi-agent-research](../research/notes/blog-multi-agent-research.md)

**Evaluator-optimizer** — One LLM generates, another critiques against a rubric, loop repeats. Best when there's a reliable evaluation signal and iteration genuinely improves output (literary translation, multi-pass research). Runs generation and evaluation in **separate sessions** to avoid confirmation bias — see [evals](evals.md) and [enforcement-reliability](enforcement-reliability.md). [blog-building-effective-agents](../research/notes/blog-building-effective-agents.md)

**Subagent design (the delegation layer)** — Subagents are exposed to the main agent as tools it calls with a prompt. They serve two jobs: **parallelize independent work** and **isolate context** (offload tens of thousands of tokens off the main window). Anthropic found Claude, like a first-time manager, gives vague delegation instructions unless the decomposition is explicit — each subagent needs objective, output format, tool guidance, and clear boundaries, or you get duplicate work and gaps. Subagents can write outputs to a shared filesystem and return lightweight references instead of piping large results through conversation history. [building-more-effective-agents](../research/notes/building-more-effective-agents.md), [blog-multi-agent-research](../research/notes/blog-multi-agent-research.md)

**Long-horizon / checkpointing** — Tasks exceeding one context window need one of three approaches: **compaction** (summarize as you near the limit), **structured note-taking** (a running NOTES.md as external memory), or **sub-agent architectures** (clean context per subtask, condensed summaries back). Production multi-agent systems are long-running and stateful, so **resumable checkpoints are mandatory** — errors compound early, and agents should continue from saved state rather than restart. [blog-context-engineering](../research/notes/blog-context-engineering.md), [blog-multi-agent-research](../research/notes/blog-multi-agent-research.md); see [context-engineering](context-engineering.md) and [memory-and-compounding](memory-and-compounding.md).

**Always-on / scheduled (the "loop")** — A recurring, cron-triggered agent that wakes on a schedule (or an event), refreshes its context, does bounded work, and reports — no human polling. Cherny calls loops "the future" and runs them to babysit PRs/CI (auto-rebase, fix flaky tests) and cluster Twitter feedback every ~30 minutes; the management pattern is dozens of background agents doing periodic work rather than one long session. [cherny-sequoia-ascent](../research/notes/cherny-sequoia-ascent.md), [behind-craft-jess-yan](../research/notes/behind-craft-jess-yan.md). Its enabling primitives are self-recovery (the agent detects and fixes its own divergence — see [enforcement-reliability](enforcement-reliability.md)) and a separate eval context to grade the work without confirmation bias.

**Outcome optimization (declarative delegation)** — Instead of dispatching subtasks with rigid intermediate output schemas that a coordinator must glue together, specify the *desired outcome or metric* and let the agent iterate internally to reach it. Jess Yan: "the outcome has become the structured output… we're just skipping straight ahead." Scales better than prescribing exact structure when the model is capable enough to self-correct, and pairs naturally with the loop and evaluator-optimizer patterns. [behind-craft-jess-yan](../research/notes/behind-craft-jess-yan.md).

## Numbers & rules of thumb

- **~15x tokens** — multi-agent research vs. normal chat; **~4x** vs. single-agent. Only justified for high-value tasks. [blog-multi-agent-research](../research/notes/blog-multi-agent-research.md)
- **90.2%** — improvement of Opus orchestrator + Sonnet subagents over single Opus on internal research eval. [blog-multi-agent-research](../research/notes/blog-multi-agent-research.md)
- **~80% of performance variance explained by token usage alone**; remaining ~15% from tool-call count and model choice. [blog-multi-agent-research](../research/notes/blog-multi-agent-research.md)
- **Up to 90% time reduction** from parallel tool calls (3–5 subagents concurrently, 3+ calls each in parallel). [blog-multi-agent-research](../research/notes/blog-multi-agent-research.md)
- **~40% faster** completion after Claude rewrote its own flawed tool descriptions. [blog-multi-agent-research](../research/notes/blog-multi-agent-research.md)
- **Scale effort to query complexity**: fact lookup = 1 agent, 3–10 tool calls; comparison = 2–4 subagents, 10–15 calls each; broad research = 10+ subagents. [blog-multi-agent-research](../research/notes/blog-multi-agent-research.md)
- **~20 representative queries** are enough to detect signal early; big prompt changes swing success **30%→80%**. [blog-multi-agent-research](../research/notes/blog-multi-agent-research.md)
- **~20 tools per agent** (bucketing) when facing a 100–200 tool vocabulary. [building-more-effective-agents](../research/notes/building-more-effective-agents.md)
- Typical agentic loop: **10–100 tool calls** per task, each **100–1,000 tokens**. For current 1M-context-class models (Opus 4.6/4.7/4.8, Sonnet 4.6/5, Fable 5, Mythos 5), **1M tokens is now the default** — no beta header, standard pricing across the full window; the older "200K default / 1M beta" framing is stale (some models, e.g. Sonnet 4.5/Opus 4.5/Haiku 4.5, remain 200K-only). [building-future-of-agents](../research/notes/building-future-of-agents.md)
- Subagents currently run **synchronously** — lead agent waits; a slow subagent stalls the system. Async would add parallelism at the cost of state/ordering complexity. [blog-multi-agent-research](../research/notes/blog-multi-agent-research.md)

## Where speakers disagree

- **More orchestration vs. less scaffolding.** The five-patterns framing treats multi-agent as the top of a deliberate complexity ladder ([blog-building-effective-agents](../research/notes/blog-building-effective-agents.md)). The unhobbling camp argues that as models improve, *scaffolding should shrink*, not grow — heavy structure prevents the model from leveraging its own intelligence ([building-future-of-agents](../research/notes/building-future-of-agents.md)). Both are Anthropic, and the tension is real: how much structure is "enough."

- **Build agents vs. build skills.** The orchestration literature spends its effort designing agent topologies. Zhang & Murag argue the field should "stop rebuilding agents and start building skills" — a single code-execution loop plus a skill library out-generalizes bespoke multi-agent scaffolds ([dont-build-agents-build-skills](../research/notes/dont-build-agents-build-skills.md)). Not a flat contradiction, but a genuine disagreement about where the leverage lives.

- **When is multi-agent worth it.** The research post is bullish on orchestrator-workers *for research/discovery* but explicitly warns it's a poor fit for coding, where high interdependency demands shared context ([blog-multi-agent-research](../research/notes/blog-multi-agent-research.md)). So "multi-agent is powerful" and "multi-agent is usually wrong for your task" are both true depending on task structure.

## Interview-ready takes

1. **"The pattern is chosen by task structure, not ambition."** Decomposable, loosely-coupled discovery → orchestrator-workers. Tightly-interdependent reasoning (most coding) → single agent with shared context. Multi-agent's ~15x token cost is only repaid when subproblems genuinely parallelize. [blog-multi-agent-research](../research/notes/blog-multi-agent-research.md)

2. **"Climb the complexity ladder; don't teleport to the top."** Single-shot → agent loop → workflows of agents → multi-agent. Each rung must demonstrably beat the one below on a real eval before you add it, because complexity compounds debugging difficulty. [building-more-effective-agents](../research/notes/building-more-effective-agents.md)

3. **"Delegation is a management skill Claude has to be taught."** Vague subagent prompts ("research X") cause duplicate work and gaps; explicit objective + output format + tool guidance + boundaries is what makes orchestrator-workers actually work. Model the agent's mind by simulating it step-by-step to find real failure modes. [blog-multi-agent-research](../research/notes/blog-multi-agent-research.md)

4. **"Long-horizon reliability is an engineering problem, not a prompting one."** Resumable checkpoints, tracing, rainbow deployments, and one of {compaction, note-taking, sub-agents} for context — errors compound early in stateful systems, so recovery must be programmatic, not hoped-for. [blog-multi-agent-research](../research/notes/blog-multi-agent-research.md), [blog-context-engineering](../research/notes/blog-context-engineering.md)

5. **"Evaluate the end state, not the trajectory."** Multi-agent systems have no single correct path; grade outcome + process reasonableness with an LLM-as-judge rubric, and keep generation and evaluation in separate sessions. [blog-multi-agent-research](../research/notes/blog-multi-agent-research.md)
