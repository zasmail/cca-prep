# Evals

## The thread

Anthropic's builders converge on a blunt claim: **evals are the primary mechanism that separates real regressions from noise**, and teams without them debug reactively — waiting for user complaints, reproducing, fixing, and hoping nothing else broke ([blog-demystifying-evals](../research/notes/blog-demystifying-evals.md)). Manual testing works at the start and breaks down at scale. The eval suite becomes the shared language between product and research teams for what to optimize, and the thing that lets you adopt a new model release in *days instead of weeks*.

The single most-repeated principle is **grade the outcome, not the exact path**. Non-deterministic agents find valid alternate routes; scoring the turn-by-turn trajectory penalizes correct behavior and rewards overfitting. You check the final state of the world — did the DB actually get updated, did the test suite pass — not whether the agent took the steps you imagined ([blog-demystifying-evals](../research/notes/blog-demystifying-evals.md), [blog-multi-agent-research](../research/notes/blog-multi-agent-research.md)). This pairs with grader discipline: prefer deterministic, code-based graders (exact match, static analysis, outcome checks) wherever possible; reserve LLM-as-judge for genuinely subjective quality; always calibrate model graders against humans. See [enforcement-reliability](enforcement-reliability.md) — the same "programmatic where it must be guaranteed" instinct governs grader choice.

The second thread is that **evals are infrastructure, not a one-time artifact**. You start small — 20-50 tasks drawn from real failures beats waiting to build hundreds — then grow deliberately: convert existing manual checks and bug-tracker issues into cases, write unambiguous tasks with reference solutions, build balanced problem sets, isolate the harness, design graders, and *read the transcripts*. Reading transcripts is non-negotiable: it is the only way to know whether a low score is a broken grader or a genuine agent mistake ([blog-demystifying-evals](../research/notes/blog-demystifying-evals.md)). Tool builders run the same loop — prototype, evaluate on realistic chained tasks, analyze reasoning traces, refine — treating eval transcripts as debugging infrastructure ([blog-writing-tools](../research/notes/blog-writing-tools.md)).

Finally, non-determinism forces you to pick the **right reliability metric for the archetype**. Coding agents where any one success suffices care about pass@k; customer-facing agents that must behave consistently every time care about pass^k. This connects to the deeper "nines of reliability" argument — long-horizon agents fail because chaining steps multiplies failure probability, not because context runs out ([dwarkesh-sholto-trenton](../research/notes/dwarkesh-sholto-trenton.md)). Your metric has to match what "working" means for the product.

## Patterns

**Grade outcomes, not paths.** Evaluate the end state achieved (world state, backend DB, whether tests now pass), not the exact turn sequence. Use when agents have latitude to reach a goal multiple ways — i.e. almost always. Give partial credit for multi-step tasks. Source: [blog-demystifying-evals](../research/notes/blog-demystifying-evals.md), [blog-multi-agent-research](../research/notes/blog-multi-agent-research.md).

**LLM-as-judge with a per-dimension rubric.** Score open-ended output against a unified rubric — the multi-agent research judge scored factual accuracy, citation accuracy, completeness, source quality, and efficiency as separate dimensions, producing a 0–1 score plus pass/fail on outcome ([blog-multi-agent-research](../research/notes/blog-multi-agent-research.md)). Variants: rubric scoring, pairwise comparison, reference-based grading, multi-judge consensus. Use for subjective quality where code graders can't reach. Always give the judge an "Unknown" escape hatch and calibrate against humans ([blog-demystifying-evals](../research/notes/blog-demystifying-evals.md)).

**Calibration against humans.** Human graders (SME review, inter-annotator agreement) are the gold standard, used specifically to *calibrate* LLM judges — Descript moved to LLM grading plus periodic human calibration. Use human studies for calibration passes, not for the whole suite (too slow/expensive). Source: [blog-demystifying-evals](../research/notes/blog-demystifying-evals.md).

**Capability vs. regression evals.** Capability evals ("what can it do?") start at low pass rates with an improvement target; regression evals ("does it still work?") should sit near 100% and any drop signals a break. Saturated capability evals graduate into the regression suite. Source: [blog-demystifying-evals](../research/notes/blog-demystifying-evals.md).

**Evals as CI / pre-launch gate.** Automated evals run pre-launch and in CI (fast, reproducible, no user impact); production monitoring and A/B tests run post-launch; feedback and manual review run continuously — the "Swiss Cheese" layering. Source: [blog-demystifying-evals](../research/notes/blog-demystifying-evals.md). Unit tests are the pragmatic default grader for coding work ([mlops-342-bidasaria](../research/notes/mlops-342-bidasaria.md)).

**20-50 tasks from real failures.** Seed the suite from actual production failures and bug reports rather than synthetic cases. Real failure cases with human-validated solutions are also the most powerful few-shot examples ([prompting-101](../research/notes/prompting-101.md)). Source: [blog-demystifying-evals](../research/notes/blog-demystifying-evals.md).

**Balanced (adversarial) problem sets.** Test both where a behavior *should* trigger and where it *shouldn't* — Claude.ai web search needed "should search" and "shouldn't search" cases to avoid over/under-triggering. This is the practical face of adversarial testing: probe the boundary in both directions. Source: [blog-demystifying-evals](../research/notes/blog-demystifying-evals.md).

**Isolated harness per trial.** Clean environment for every trial; shared state causes correlated failures or unfair advantages (an agent peeking at leftover git history from a prior trial). Run multiple trials because models are non-deterministic. Source: [blog-demystifying-evals](../research/notes/blog-demystifying-evals.md).

**Per-type / per-field metrics.** Aggregate accuracy hides failure. Evaluate by agent archetype (coding needs test execution + static analysis; conversational needs user-simulation + outcome checks; research needs groundedness + coverage; computer-use must check backend state, not just UI). For extraction, track per-document-type and per-field accuracy, not one blended number. Source: [blog-demystifying-evals](../research/notes/blog-demystifying-evals.md); see [gtm-applications](gtm-applications.md).

**Model-migration testing.** A mature suite validates a new model in days — but only if graders aren't overfit to the old model's output style. Rigid graders can *undervalue* a genuinely better model (see CORE-Bench below). Source: [blog-demystifying-evals](../research/notes/blog-demystifying-evals.md).

**Anchor evals to real customer use cases, not synthetic benchmarks.** Synthetic benchmarks miss the true task shape; only evals tied to how actual users will experience the model surface meaningful gaps. As few as *dozens* of well-chosen cases (not thousands) can identify and validate a gap, which then feeds a gap → synthetic-test-case → hypothesis → intervention → hill-climb pipeline. Source: [behind-craft-alex-albert](../research/notes/behind-craft-alex-albert.md).

**Character / qualitative eval.** Some targets aren't a pass/fail on a task at all — an agent's *character* (how often it pushes back, whether it over-agrees) governs unsupervised judgment quality. Evaluate it as a hybrid: a quantitative metric (e.g. pushback frequency) plus qualitative pattern-recognition from reading transcripts. Source: [behind-craft-alex-albert](../research/notes/behind-craft-alex-albert.md); see [enforcement-reliability](enforcement-reliability.md).

## Numbers & rules of thumb

- **20-50 tasks from real failures** to start — beats waiting to build hundreds ([blog-demystifying-evals](../research/notes/blog-demystifying-evals.md)).
- **~20 representative queries** were enough to detect signal early in multi-agent research; prompt changes swung success **30% → 80%** ([blog-multi-agent-research](../research/notes/blog-multi-agent-research.md)).
- **pass^k example:** 75% single-trial success → all-3-succeed ≈ **42%** (0.75³). pass@k rises with k, pass^k falls with k; identical at k=1 ([blog-demystifying-evals](../research/notes/blog-demystifying-evals.md)).
- **0% pass@100 usually means a broken task/grader, not an incapable model** — a frontier model should never score zero across many trials ([blog-demystifying-evals](../research/notes/blog-demystifying-evals.md)).
- **CORE-Bench:** Opus 4.5 scored **42%** due to rigid numeric grading (rejecting "96.12" vs. a long expected decimal); reached **95%** after grader fixes ([blog-demystifying-evals](../research/notes/blog-demystifying-evals.md)).
- **SWE-Bench Verified:** ~30–40% → **80%+ within one year** — capability evals saturate fast; plan the transition to regression ([blog-demystifying-evals](../research/notes/blog-demystifying-evals.md)).
- **Bolt** built a working eval system in **~3 months** (static analysis + browser-agent testing + LLM judges) ([blog-demystifying-evals](../research/notes/blog-demystifying-evals.md)).
- **~40% faster task completion** after Claude rewrote flawed tool descriptions, caught via eval transcripts ([blog-multi-agent-research](../research/notes/blog-multi-agent-research.md)).
- Correctness checking spans **exact string match → Claude-based judge**; pick the cheapest grader that still captures correctness ([blog-writing-tools](../research/notes/blog-writing-tools.md)).

## Where speakers disagree

**Code graders vs. LLM graders — brittleness cuts both ways.** The demystifying-evals guidance says *prefer deterministic code graders* because they're fast, cheap, and objective. But the same source's own case studies (CORE-Bench 42%, METR's backwards τ-Bench threshold logic) are all failures *caused by* rigid code graders penalizing correct answers. The tension is real: deterministic graders are safer against gaming but brittle to valid variation; LLM graders tolerate variation but are non-deterministic and gameable in the other direction. The resolution the source lands on — read transcripts, calibrate, give partial credit — is a hedge, not a clean rule ([blog-demystifying-evals](../research/notes/blog-demystifying-evals.md)).

**How much can you trust the trajectory?** Grading outcomes assumes the path is noise. But Sholto/Trenton argue chain-of-thought reasoning is often *unfaithful* — it can be deleted or garbled without changing the answer ([dwarkesh-sholto-trenton](../research/notes/dwarkesh-sholto-trenton.md)) — which cuts against process-based grading of reasoning traces even where you might want it. Meanwhile the multi-agent judge does score *process reasonableness* as one dimension. So there's a live tension: outcome-only grading is robust but blind to *how* an answer was reached, and reasoning traces are exactly the thing that may be unfaithful.

**Start narrow vs. cover the space.** "Start with 20-50 tasks" (ship fast, learn) sits against the "balanced problem set / per-type per-field" imperative (cover both trigger and non-trigger cases, every document type). Both are in the same source; the practical read is *sequence* them — start narrow, then broaden — but a naive 20-task suite that only tests the happy path will give false confidence ([blog-demystifying-evals](../research/notes/blog-demystifying-evals.md)).

## Interview-ready takes

1. **"Grade the outcome, not the path."** Non-deterministic agents find valid alternate routes; scoring the trajectory penalizes correct behavior and rewards overfitting. Check the end state of the world. Grounded in [blog-demystifying-evals](../research/notes/blog-demystifying-evals.md) and the multi-agent judge that scored end-state achieved, not turn sequence ([blog-multi-agent-research](../research/notes/blog-multi-agent-research.md)).

2. **"pass@k and pass^k answer different product questions."** A coding agent where one success suffices optimizes pass@k; a customer-facing agent that must be consistent every time optimizes pass^k — and 75% single-trial reliability is only ~42% over three consecutive turns. Mismatching the metric hides instability ([blog-demystifying-evals](../research/notes/blog-demystifying-evals.md)), and it's the eval-side expression of "nines of reliability" ([dwarkesh-sholto-trenton](../research/notes/dwarkesh-sholto-trenton.md)).

3. **"A 0% score is a bug in your eval, not your model."** A frontier model scoring 0% across 100 trials almost always means a broken task or grader. This flips the reflexive "the model can't do it" and forces you to read transcripts first — the only way to tell a fair grader from a genuine mistake ([blog-demystifying-evals](../research/notes/blog-demystifying-evals.md)).

4. **"Aggregate accuracy is a lie; report per-type and per-field."** One blended number hides which document type or field is failing. Evaluate by agent archetype and, for extraction, per-document-type and per-field — this is anti-pattern #10 in the CCA-F canon ([blog-demystifying-evals](../research/notes/blog-demystifying-evals.md)).

5. **"Evals are infrastructure with an owner, and they run in CI."** Start with 20-50 real failures, convert bug reports into cases, layer automated evals (pre-launch/CI) with monitoring and A/B tests (post-launch) — the Swiss Cheese model — and give the suite a dedicated long-term owner so it doesn't rot. This is what lets you migrate models in days ([blog-demystifying-evals](../research/notes/blog-demystifying-evals.md)); unit tests are the pragmatic default grader for coding work ([mlops-342-bidasaria](../research/notes/mlops-342-bidasaria.md)).
