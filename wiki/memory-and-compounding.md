# Memory & Compounding

How agents carry state across turns and sessions, and how that state can be made to *compound* — get more valuable over time — rather than being re-derived from scratch on every query.

## The thread

The field's builders have converged on a blunt architectural fact: today's LLMs have no persistent episodic memory and no sleep-like consolidation step. Karpathy names this directly as one of the core cognitive gaps — "no hippocampus-equivalent... no sleep-like consolidation/distillation step" ([dwarkesh-karpathy](../research/notes/dwarkesh-karpathy.md)). Weights hold only "hazy recollection" of a huge corpus compressed into a comparatively tiny parameter count; anything in the context window is *directly accessible*. So the entire practical game of agent memory is: what do you write into an external, durable store, and how cheaply can you get the right slice of it back into the window when it matters. Memory is a file-system-and-retrieval problem, not a model problem.

The most load-bearing idea for interviews is the distinction between **compounding** and **re-retrieval**. Classic RAG re-derives an answer by pulling raw chunks at query time — every question starts cold. Karpathy's LLM Wiki inverts this: have an agent *incrementally build and maintain a persistent wiki* of LLM-generated markdown so that synthesis accumulates across sessions instead of being recomputed each time ([karpathy-llm-wiki](../research/notes/karpathy-llm-wiki.md)). The wiki is not the raw documents; it is the model's *distilled understanding* of them, refined over time. The tax you pay for this is bookkeeping — "the tedious part of maintaining a knowledge base is not the reading or the thinking, it's the bookkeeping" ([karpathy-llm-wiki](../research/notes/karpathy-llm-wiki.md)) — which is exactly the part agents can now automate.

Anthropic's product surface encodes the same instinct at three altitudes. `CLAUDE.md` is living memory loaded at the start of every session — the schema layer of a wiki, a declaration of structure and conventions. A running `NOTES.md` is *structured external memory* that keeps an agent coherent across a multi-hour task ([blog-context-engineering](../research/notes/blog-context-engineering.md)). And Skills are the compounding layer for *procedural* knowledge: "anything that Claude writes down can be used efficiently by a future version of itself... this makes the learning actually transferable," so a Day-30 agent is materially better than a Day-1 agent through accumulated skills ([dont-build-agents-build-skills](../research/notes/dont-build-agents-build-skills.md)). See [skills-and-progressive-disclosure](skills-and-progressive-disclosure.md) and [context-engineering](context-engineering.md) for the mechanics.

The unifying principle: because context is a finite resource with "diminishing marginal returns, analogous to limited human working memory" ([blog-context-engineering](../research/notes/blog-context-engineering.md)), memory systems win by writing *distilled, high-signal* artifacts to durable storage and pulling them back just-in-time — not by cramming ever-more raw text into the window.

## Patterns

**Agent-maintained wiki (compounding memory).** An LLM incrementally builds interlinked markdown pages — summaries, entities, concepts — so knowledge is synthesized once and refined thereafter, not re-derived per query. Use when the same knowledge base is queried repeatedly over time (team wikis, research deep-dives, competitive analysis, code-review context). Contrast with RAG, which suits one-off retrieval over a corpus you don't revisit. Source: [karpathy-llm-wiki](../research/notes/karpathy-llm-wiki.md).

**Three-layer architecture.** (1) *Raw sources* — immutable originals, never modified by the LLM; (2) *the wiki* — LLM-generated pages; (3) *the schema* (e.g. `CLAUDE.md`) — config defining structure and workflows. Separating immutable ground truth from mutable synthesis makes the system auditable and lets you regenerate the middle layer if it drifts. Source: [karpathy-llm-wiki](../research/notes/karpathy-llm-wiki.md).

**Ingest → Query → Lint.** The three canonical operations that keep a wiki healthy. *Ingest* processes new sources and updates cross-references; *Query* searches and synthesizes, optionally filing the result back as a new page (this is the compounding step); *Lint* health-checks for contradictions, orphan pages, and stale claims. Use whenever a knowledge store is long-lived and multiple agents/sessions write to it. Source: [karpathy-llm-wiki](../research/notes/karpathy-llm-wiki.md).

**Append-only log + content index.** A chronological `log.md` (append-only, never mutate history — enables audit and replay) paired with a content-oriented `index.md` catalog for navigation. Treated as essential supporting artifacts, not optional. Use for any stateful, multi-session system where you need to reconstruct *why* the store looks the way it does. Source: [karpathy-llm-wiki](../research/notes/karpathy-llm-wiki.md); resonates with the resumable-checkpoint discipline in [orchestration-patterns](orchestration-patterns.md) ([blog-multi-agent-research](../research/notes/blog-multi-agent-research.md)).

**Structured external memory (`NOTES.md`).** Agent maintains a running notes file so it stays coherent across a task longer than one context window. Chosen for *iterative build work*, where compaction would lose too much. Source: [blog-context-engineering](../research/notes/blog-context-engineering.md).

**CLAUDE.md as living memory.** A file read at the start of every session, ruthlessly pruned by the "would removing this line cause a mistake?" test. Hierarchical (global → project → directory → `@import`), with only project-level-and-below shared via VCS. It is memory *and* schema — persistent cross-session state that a bloated file destroys, because Claude starts ignoring parts of it. Source: [blog-claude-code-best-practices](../research/notes/blog-claude-code-best-practices.md). See [claude-code-workflows](claude-code-workflows.md).

**Skills as compounding procedural memory.** Standardized folders that let an agent's output (a new skill) be consumed by future agent versions. Use to capture *how-to* knowledge (workflows, scripts, org best practices) that should survive across sessions and users. Source: [dont-build-agents-build-skills](../research/notes/dont-build-agents-build-skills.md).

**Cognitive core + external memory.** Deliberately split a small reasoning model ("cognitive core") from bulk factual memory living in external lookup, so you don't pay to carry trivia in weights. The architectural mirror of the wiki pattern at the model level. Source: [dwarkesh-karpathy](../research/notes/dwarkesh-karpathy.md); see [karpathy-mental-models](karpathy-mental-models.md).

**Memory reconsolidation ("dreaming").** An off-task pass in which the agent walks its own accumulated memories, finds contradictions, prunes and cleans them up — the engineered analog of sleep-time consolidation. Anthropic ships it: overnight pruning on Claude.ai, background consolidation on managed agents. Use it to stop long-running agents from drifting as their memory store accumulates contradictions. This is the *lint* step of Karpathy's wiki running as a scheduled background job. Source: [behind-craft-alex-albert](../research/notes/behind-craft-alex-albert.md).

## Numbers & rules of thumb

- **Bookkeeping, not reading, is the cost** of maintaining a knowledge base — the part worth automating ([karpathy-llm-wiki](../research/notes/karpathy-llm-wiki.md)).
- **Prune CLAUDE.md by the "would removing this line cause a mistake?" test**; bloat causes Claude to ignore parts of it ([blog-claude-code-best-practices](../research/notes/blog-claude-code-best-practices.md)).
- **Only project-level-and-below CLAUDE.md is shared via VCS**; `~/.claude/CLAUDE.md` and `CLAUDE.local.md` are personal ([blog-claude-code-best-practices](../research/notes/blog-claude-code-best-practices.md)).
- **Choose the memory strategy by task shape:** compaction for long conversations, note-taking (`NOTES.md`) for iterative build work, sub-agents for complex research ([blog-context-engineering](../research/notes/blog-context-engineering.md)).
- **Context degrades gradually ("context rot"), not off a cliff** — rooted in transformer n² attention and thin training exposure to very long sequences ([blog-context-engineering](../research/notes/blog-context-engineering.md)).
- **Day-30 agent > Day-1 agent** via accumulated skills — the compounding claim in one line ([dont-build-agents-build-skills](../research/notes/dont-build-agents-build-skills.md)).
- **LeadResearcher persists its plan to memory at the 200K-token context ceiling** so a truncation doesn't lose the strategy ([blog-multi-agent-research](../research/notes/blog-multi-agent-research.md)).
- **Recommended wiki search tool: `qmd`** (hybrid BM25/vector) — retrieval quality is part of the memory system, not an afterthought ([karpathy-llm-wiki](../research/notes/karpathy-llm-wiki.md)).

## Where speakers disagree

**Distill-into-weights vs. keep-in-context.** Karpathy argues weights should hold a small *cognitive core* and offload facts to external memory, because "you can't think if you're looking things up constantly" — some baseline knowledge must be internal ([dwarkesh-karpathy](../research/notes/dwarkesh-karpathy.md)). The context-engineering camp pushes the opposite direction for *practical agents today*: keep raw ground truth external and pull it just-in-time, because in-context access beats hazy weight recollection ([blog-context-engineering](../research/notes/blog-context-engineering.md)). The tension is real — how much should live *in* the model vs. *beside* it — even though both agree the two should be separated.

**Compounding synthesis vs. lossless re-retrieval.** The wiki bets on storing the agent's *interpretation* so synthesis accumulates ([karpathy-llm-wiki](../research/notes/karpathy-llm-wiki.md)). But an LLM-generated wiki can propagate and entrench errors — which is precisely why *Lint* (contradiction/stale-claim detection) is a first-class operation, and why classic RAG's re-derivation from immutable raw chunks remains safer for high-stakes factual lookup. Compounding trades freshness and auditability for cheaper, richer synthesis.

**Is consolidation solvable outside the model?** Karpathy frames the absence of a "sleep-like consolidation" step and even speculates that *dreaming* injects entropy to prevent human cognitive over-fitting / model collapse ([dwarkesh-karpathy](../research/notes/dwarkesh-karpathy.md)) — implying real memory may need mechanisms we can't fake with files. Anthropic's practical stance is that compaction, note-taking, and skill accumulation are a *good-enough* external substitute today ([blog-context-engineering](../research/notes/blog-context-engineering.md), [dont-build-agents-build-skills](../research/notes/dont-build-agents-build-skills.md)). And Anthropic has gone further than "good enough": Alex Albert describes an actual shipped "dreaming" mechanism — off-task memory pruning that resolves contradictions, run overnight on Claude.ai and in the background on managed agents, explicitly to increase consistency in long-running agents ([behind-craft-alex-albert](../research/notes/behind-craft-alex-albert.md)). So the gap Karpathy calls architectural is at least partly being *productized* as a scheduled external process — evidence for the engineerable-now camp, even if it doesn't touch the weights.

## Interview-ready takes

1. **"Memory is a retrieval-and-write-back problem, not a model feature."** LLMs lack episodic memory and consolidation ([dwarkesh-karpathy](../research/notes/dwarkesh-karpathy.md)); durable state lives in files. The design question is always *what distilled artifact do I write, and how do I pull the right slice back just-in-time* ([blog-context-engineering](../research/notes/blog-context-engineering.md)).

2. **"Compounding beats re-retrieval when the corpus is revisited."** RAG re-derives cold every query; an agent-maintained wiki synthesizes once and refines, so knowledge gets *cheaper and better* over time — at the cost of bookkeeping and a lint step to catch drift ([karpathy-llm-wiki](../research/notes/karpathy-llm-wiki.md)).

3. **"Separate immutable sources, mutable synthesis, and schema."** The three-layer architecture makes memory auditable: you can always regenerate the LLM layer from raw sources, and the schema (`CLAUDE.md`) declares the rules ([karpathy-llm-wiki](../research/notes/karpathy-llm-wiki.md), [blog-claude-code-best-practices](../research/notes/blog-claude-code-best-practices.md)).

4. **"Skills are how procedural memory compounds across sessions and users."** Because a standardized skill written by one agent is consumable by the next, org knowledge accumulates without retraining — Day 30 >> Day 1 ([dont-build-agents-build-skills](../research/notes/dont-build-agents-build-skills.md)). See [skills-and-progressive-disclosure](skills-and-progressive-disclosure.md).

5. **"Append-only logs and pruned CLAUDE.md are enforcement, not hygiene."** An append-only `log.md` gives you replay and audit for stateful multi-session systems ([karpathy-llm-wiki](../research/notes/karpathy-llm-wiki.md)); a pruned CLAUDE.md is what keeps persistent memory from being *ignored* — bloat silently defeats it ([blog-claude-code-best-practices](../research/notes/blog-claude-code-best-practices.md)). Ties to [enforcement-reliability](enforcement-reliability.md).
