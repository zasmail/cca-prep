# Context Engineering

*Context as the scarce resource: context rot, compaction, /clear discipline, subagent isolation, prompt caching economics, long-context tradeoffs, Goldilocks-zone instructions, CLAUDE.md design.*

## The thread

The field's builders converge on one reframing: the context window is a **finite resource with diminishing marginal returns**, not free real estate to fill. Anthropic's Applied AI team names the discipline explicitly — context engineering is "optimizing which tokens occupy an LLM's limited context window during inference," and it differs from prompt engineering because it is **iterative and repeats every turn**, not a one-time authoring task ([blog-context-engineering](../research/notes/blog-context-engineering.md)). The physical basis is **context rot**: model accuracy degrades as the window fills, rooted in the transformer's n² pairwise attention and thinner training exposure to very long sequences. Crucially it is a gradual slope, not a cliff — which is exactly why it gets ignored until an agent is "forgetting earlier instructions" mid-task ([blog-claude-code-best-practices](../research/notes/blog-claude-code-best-practices.md)).

The prescription is uniform across sources: **keep context minimal and high-signal.** The goal is stated identically to a compression objective — "find the smallest set of high-signal tokens that maximizes the chance of the desired outcome" ([blog-context-engineering](../research/notes/blog-context-engineering.md)). Karpathy supplies the mental model underneath: in-context learning is the model's most impressive capability because anything in the window is *directly accessible*, whereas weights hold only "hazy recollection." Context is working memory; you don't fill working memory with trivia ([dwarkesh-karpathy](../research/notes/dwarkesh-karpathy.md)). This is why the whole [tool-design-and-mcp](tool-design-and-mcp.md) and [skills-and-progressive-disclosure](skills-and-progressive-disclosure.md) agenda is really a context-engineering agenda in disguise — tools and skills are levers for keeping tokens out of the window until they earn their place.

The practical philosophy, from the Claude Code team, is **"do the simple thing first."** They consciously resisted elaborate memory and retrieval systems: autocompact (ask the model to summarize its own prior turns) is called "crude but effective" and reportedly beats fancier memory architectures; runtime agentic search (grep/glob) beat pre-built RAG indexes on performance while avoiding staleness and security risk ([latent-space-claude-code](../research/notes/latent-space-claude-code.md)). The throughline for an interview: context management is not a feature you bolt on, it is the primary design constraint that shapes tool schemas, retrieval strategy, orchestration topology, and CLAUDE.md itself.

## Patterns

**Just-in-time retrieval.** Fetch data during execution via tools and lightweight references (file paths, IDs, links) rather than pre-loading blobs. Metadata in references — folder structure, naming conventions, timestamps — gives signal without loading content. Trade-off: slower runtime exploration vs. less context pollution; a **hybrid** (bootstrap metadata upfront + on-demand pulls) is usually the sweet spot ([blog-context-engineering](../research/notes/blog-context-engineering.md)). Use when the corpus is large or fast-changing.

**Compaction.** Summarize the conversation as it nears the window limit — keep key decisions and bugs, drop redundant tool output. Best for long back-and-forth conversations. In Claude Code, guided via `/compact <instructions>`, and CLAUDE.md can declare what to always preserve ([blog-claude-code-best-practices](../research/notes/blog-claude-code-best-practices.md)).

**Context editing (clear stale tool results).** Distinct from compaction: instead of summarizing the whole conversation, *strip* old tool-call results that are no longer load-bearing — "tool results from past calls are not necessarily super relevant later in a session." Pair it with a memory tool (store context outside the window, retrieve on demand). This isn't hygiene: combining memory + context editing produced a **39% performance gain** on Anthropic's internal agent evals, which reframes context management as a measurable capability lever, not cleanup ([evolving-claude-apis](../research/notes/evolving-claude-apis.md)). The mental model is a three-tier stratification — *in-window* (current), *stored* (memory), *cleared* (edited out) — and larger windows only help when paired with these editing tools plus Claude's learned sense of remaining space.

**Structured external memory (NOTES.md).** The agent maintains a running notes file so it stays coherent across a multi-hour task that exceeds one window. Best for iterative build work. This generalizes to Karpathy's LLM-wiki: an LLM-*generated* markdown layer that compounds synthesis over time, vs. classic RAG that re-derives answers from raw chunks each query ([karpathy-llm-wiki](../research/notes/karpathy-llm-wiki.md)). See [memory-and-compounding](memory-and-compounding.md).

**Subagent isolation.** Specialized subagents handle narrow tasks in their own clean context windows and return only condensed summaries to a coordinator. Best for complex research where surface area exceeds one window ([blog-context-engineering](../research/notes/blog-context-engineering.md), [blog-multi-agent-research](../research/notes/blog-multi-agent-research.md)). See [orchestration-patterns](orchestration-patterns.md).

**Progressive disclosure.** Load tool/skill definitions in tiers — metadata → body → bundled files — so complexity never bloats the window upfront ([blog-agent-skills](../research/notes/blog-agent-skills.md)). Its aggressive cousin is **code execution over tool calls**: represent MCP servers as typed code APIs, load tool defs on demand, and filter/transform intermediate results *before* the model sees them ([blog-code-execution-mcp](../research/notes/blog-code-execution-mcp.md)).

**Goldilocks-zone instructions.** System prompts pitched at the right altitude — specific enough to steer, expressed as flexible heuristics, not brittle if/then logic. Diverse canonical few-shot examples beat exhaustive edge-case enumeration ([blog-context-engineering](../research/notes/blog-context-engineering.md)).

**/clear discipline.** Reset context between unrelated tasks; kitchen-sink sessions are a named failure mode. After **2 failed corrections** on the same issue, `/clear` and rewrite beats continued patching — "a clean session with a sharper prompt usually beats a long polluted one" ([blog-claude-code-best-practices](../research/notes/blog-claude-code-best-practices.md)).

## Numbers & rules of thumb

- **Token usage explains ~80% of performance variance** in multi-agent research; model choice + tool-call count the remaining ~15% ([blog-multi-agent-research](../research/notes/blog-multi-agent-research.md)).
- **150,000 → 2,000 tokens (98.7% reduction)** for a Drive-to-Salesforce workflow via code execution instead of sequential tool calls ([blog-code-execution-mcp](../research/notes/blog-code-execution-mcp.md)).
- **Multi-agent costs ~15x a normal chat, ~4x single-agent** — justify subagent isolation only on high-value tasks ([blog-multi-agent-research](../research/notes/blog-multi-agent-research.md)).
- **+39% on internal evals** from combining a memory tool with context editing (clearing stale tool results) — context management measurably moves capability, not just cost ([evolving-claude-apis](../research/notes/evolving-claude-apis.md)).
- **2 failed corrections → `/clear` and rewrite** ([blog-claude-code-best-practices](../research/notes/blog-claude-code-best-practices.md)).
- **One debugging session can burn tens of thousands of tokens** — context is spent fast ([blog-claude-code-best-practices](../research/notes/blog-claude-code-best-practices.md)).
- **Attention is n² over tokens** — the structural reason for context rot ([blog-context-engineering](../research/notes/blog-context-engineering.md)).
- **Prompt caching economics** (CCA-F reference card): cache hit = **10% of base cost**; 5-min TTL = 1.25x write cost, 1-hour = 2x; minimum cacheable size is **model-dependent, not a flat rule** — 1,024 tokens for Sonnet 5/Opus 4.8, 512 for Fable 5/Mythos 5, 4,096 for Opus 4.6/Haiku 4.5, 2,048 for Haiku 3.5; up to **4 breakpoints**; prefix order **tools → system → messages** — so put stable content first and volatile content last to preserve hits.
- **CLAUDE.md pruning test:** "Would removing this line cause a mistake?" If no, cut it — bloated CLAUDE.md causes Claude to ignore parts of it ([blog-claude-code-best-practices](../research/notes/blog-claude-code-best-practices.md)).

## Where speakers disagree

**Compaction vs. external memory vs. simplicity.** The context-engineering blog treats compaction as *lossy* — for long-horizon build work it prefers structured NOTES.md, warning that single-session compaction degrades as tasks extend ([blog-context-engineering](../research/notes/blog-context-engineering.md)). The Claude Code team is more sanguine: autocompact (model self-summarization) is "crude but effective" and *outperformed* the elaborate memory systems they tried ([latent-space-claude-code](../research/notes/latent-space-claude-code.md)). The reconciliation is task shape — conversation vs. multi-hour build — but the underlying bet on how much machinery memory deserves genuinely differs.

**Big context window vs. curated context.** The instinct that 1M-token windows make curation moot runs straight into context rot: a bigger window degrades accuracy the more you fill it, so more capacity is not more usable signal ([blog-context-engineering](../research/notes/blog-context-engineering.md)). Karpathy sharpens the tension the other way — a small "cognitive core" stripped of trivia plus external retrieval could match far larger models, implying *less* baked-in context, not more ([dwarkesh-karpathy](../research/notes/dwarkesh-karpathy.md)).

**Pre-built retrieval vs. runtime search.** The Claude Code team abandoned RAG indexes for runtime grep/glob, citing performance, staleness, and security ([latent-space-claude-code](../research/notes/latent-space-claude-code.md)). Karpathy's wiki pattern leans the opposite way — a *maintained* LLM-generated knowledge layer that compounds, explicitly contrasted against re-deriving answers from raw chunks each query ([karpathy-llm-wiki](../research/notes/karpathy-llm-wiki.md)). Runtime-fresh vs. precomputed-compounding is a live tradeoff, not a settled answer.

## Interview-ready takes

1. **"Context is the scarce resource, and rot is why."** Bigger windows don't remove the constraint — n² attention plus thin long-sequence training means accuracy slopes down as you fill up. Design token budget as a first-class constraint from day one ([blog-context-engineering](../research/notes/blog-context-engineering.md)).

2. **"Token usage explains ~80% of multi-agent performance variance — so context strategy *is* the performance strategy."** Subagent isolation, code-execution filtering, and just-in-time retrieval aren't hygiene; they're the primary lever, and they cost ~15x, so reserve them for high-value work ([blog-multi-agent-research](../research/notes/blog-multi-agent-research.md), [blog-code-execution-mcp](../research/notes/blog-code-execution-mcp.md)).

3. **"Match the long-horizon technique to task shape."** Compaction for conversations, NOTES.md for iterative builds, subagents for research. Don't reach for multi-agent's 15x cost when a notes file suffices ([blog-context-engineering](../research/notes/blog-context-engineering.md)).

4. **"Prune CLAUDE.md ruthlessly; a bloated one gets ignored."** Apply the removal test, keep only non-obvious commands and gotchas, and remember that context management and [enforcement-reliability](enforcement-reliability.md) diverge — guaranteed behavior needs hooks, not more prose ([blog-claude-code-best-practices](../research/notes/blog-claude-code-best-practices.md)).

5. **"Do the simple thing first."** Autocompact and runtime search beat elaborate memory/RAG until they demonstrably fail; reach for machinery only when the simple approach breaks ([latent-space-claude-code](../research/notes/latent-space-claude-code.md)).
