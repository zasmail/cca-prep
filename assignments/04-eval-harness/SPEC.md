# A4 — The Harness

**"My accept/edit/reject decisions are the ground truth. Now a model upgrade is a Tuesday, not a rewrite."**

Build the eval harness that sales-machine's CLAUDE.md pretends already exists: turn your own draft verdicts into graded cases, grade them with deterministic checks + per-dimension LLM judges, calibrate the judges against yourself until they agree ≥80%, and use the suite to pick between two models on evidence instead of vibes.

> **Meta-rule — you type every line.** Claude Code is a reviewer and explainer here, never a source. Ask it *why* a rubric is weak; never paste a rubric it wrote. Every checkpoint below is answered in your own words in `evals/NOTES.md`. Copy-paste can't satisfy the done-criteria — they turn on judgments you made and can defend.

## Why this matters
- **Interview (D4/D5):** "Grade outcomes not paths" and "pass@k vs pass^k" are abstract until you've chosen them for a real product. After this you argue calibrated judges from *your own* decision log, not a blog post.
- **Exam D4 (prompt engineering) + D5 (context management):** LLM-as-judge rubrics and the mandatory "Unknown" escape hatch are D4; the D5 link is concrete, not decorative — calibration is a *context-budget* discipline. Reading disagreement transcripts (M4) and per-dimension reporting (M5) is deciding what evidence earns space in the window: you keep the reasoning that changed a verdict and drop the blended aggregate that hides instability. This build makes anti-pattern #10 (aggregate-only metrics) a mistake you've felt, not memorized.
- **Real infra:** This is the regression gate every later model swap in sales-machine rides on. Its deterministic grader *is* A2's `lint-draft.py` refactored (Milestone 2), and A5 (the orchestrator) calls these judges inline over drafts built from A3's signals — so the harness is where A1's, A2's, and A3's outputs all finally get held to a measured bar, not a demo.

## The build

Work in `~/dev/Autobound/sales-machine`. New code lands under `evals/`. Keep a running `evals/NOTES.md` — every checkpoint answer goes there, dated.

> **Time budget (honest):** the five milestones below sum to **~3.9–5.4 focused build-hours** (60–90 + 25–40 + 60–75 + 45–60 + 45–60 min); the ≤35-min prereq reading is separate. (M1's top end assumes genuinely varied case drafts run 4–5 min each — that's normal, not slow.) The low end sits inside the brief's 3–5-hour cap; the pessimistic high end brushes just past it, and the reason is **M1's hand-authoring load** — ~18 fresh case drafts, each typed by you (the meta-rule), varied in *both* directions. That is real writing time, not boilerplate. Two milestones are the risk: M1 (case authoring, front-loaded) and M4 (calibration is iterative — see its scope note). If you're running long, the cut order is: first spread M1's corpus across two sittings (author to the **≥20 floor**, defer the 40-50 stretch), then cut M5's stretch and the two-model *cost* write-up — but never cut reading the divergent transcripts. The transcript read is the point; the cost table is fast once you have the rates.

### Milestone 1 — Instrument decision capture, then seed to 20 cases (60–90 min)
The corpus doesn't exist. Two things: make capture frictionless going forward, and backfill enough cases to calibrate on *now*.
- **Deliverable A — `evals/capture.py`:** a tiny CLI, `capture.py <draft-path> <verdict> "<lesson>"`, that appends a row to `decisions.log` (tab-separated, matching the existing header `date draft verdict lesson`) **and** snapshots the draft's body into `evals/cases/<date>-<slug>.md` with YAML frontmatter (`verdict`, `lesson`, `source_draft`). Verdicts are the ones you already use: `PASS`, `PASS-WEAK`, `REJECT` (+ `EDIT` when you rewrote before sending). This is the append-only capture mechanism the log currently lacks — no draft should ever be judged again without a row landing here.
- **Deliverable B — seed the set:** you have 1 real draft on disk (`outbox/2026-07-13-orum-voice-sample.md`, the REJECT) and 1 row whose file is gone (`crunchbase-james.md`). Reconstruct/author **≥20 cases** total by hand-labeling drafts: pull real ones, and where you're short, write deliberately-flawed variants that probe the boundary in *both* directions (a REJECT that violates one prohibition, a PASS that's plain-but-correct). Balance matters — a 20-case set that's all happy-path gives false confidence (`evals/NOTES.md` names why).
  - **Dogfood the capture script to keep this in budget:** you type every *draft body* (the meta-rule), but you should **not** hand-type YAML frontmatter 18 times. Build Deliverable A **first**, then run it over each draft you author — `capture.py` writes the case file and the log row for you. That is also the honest answer to Checkpoint 1's ordering question, felt rather than argued: the capture script is deliverable one because it's the tool you use to build the corpus, not just a going-forward convenience.
- **Scope honestly (M1 is the heaviest hand-authoring milestone — same discipline as M4):** only **2 of the required ≥20** cases exist today, so ~18 are net-new writing at a few minutes each — plausibly the bulk of this milestone before capture.py's own code. **≥20 is the floor, not the target**; hit it, then stop. If you're running long, author to the floor across two sittings rather than padding a thin set in one — the 40-50-case expansion is explicitly a Stretch, not part of M1. Do not thin the *variety* to hit the count faster: a balanced 20 beats a lopsided 30.
- **Checkpoint 1:** In `NOTES.md`, answer: *Why is a capture script the first deliverable instead of a `decisions.log → cases` converter? What does "grade the outcome, not the path" mean for a cold-outreach draft specifically — what is the "outcome" you're grading when there's no reply-rate yet?*

### Milestone 2 — Deterministic graders: refactor the A2 linter to single-source it (25–40 min)
The cheapest grader that captures correctness wins. Some voice rules are objective — grade them in code, never with a judge. The brief says "reuse the A2 linter," and it means it literally: your `scripts/lint-draft.py` already ships every deterministic check this milestone needs. Do **not** re-implement those rules — but "reuse" here is not a one-line wrap, and the spec won't pretend it is. Two concrete obstacles you'll hit, and the intended way through both:
  1. **Your linter is CLI-shaped; a grader loop needs a library.** Post-A2, `main()` emits the structured JSON on *stdout* and gates via exit code — the right contract for a hook, the wrong shape for calibration: shelling out per case means a subprocess and a stdout-parse for every one of 20+ cases × every calibration round. So the first move is a **small, legitimate refactor of A2's file**: extract the rule logic into a pure function — e.g. `lint(path) -> (fails, warns)` returning the rule-tagged lists — and reduce `main()` to a thin wrapper that calls `lint()`, builds the JSON, and exits `0`/`2`. The CLI/hook behavior A2 depends on is unchanged; you've just made the detail importable. This is the "single-sourced, not forked" instruction made real: the hook and your grader now call one `lint()`.
  2. **The filename has a hyphen.** `import scripts.lint-draft` is a `SyntaxError`. Resolve it deliberately, not by copying the file: either **rename to `scripts/lint_draft.py`** (then update the A2 **PreToolUse** hook in `.claude/settings.json` whose command shells to it — grep for `lint-draft` there first; if the grep finds no hook, you skipped A2's M3 and should wire it before renaming anything) — the cleaner fix — or load it with `importlib.util.spec_from_file_location` if you'd rather not touch the hook. State which you chose in `NOTES.md` and why.
- **Deliverable — `evals/graders/deterministic.py`:** a thin adapter that calls the refactored `lint()` over a draft and returns the harness's **structured result** — `isError` / `errorCategory` / `isRetryable` (anti-pattern #6 — no bare booleans, no bare exit codes). Map a hard `FAIL` (e.g. a prohibition hit) to `isError=True`, a non-retryable category, and a verdict of `REJECT`; map `warn`-only to a pass with notes — and set `errorCategory` from the *rule prefix* in each `fails` entry (`R1`, `R14`, `R8`…), which is exactly the detail the refactor unlocked. If a rule you need isn't in the linter yet, add it *there* (in `lint()`) and it flows to both call sites for free.
- **Checkpoint 2:** *Which voice dimensions are deterministic (already in `lint-draft.py`) and which did you leave to an LLM judge — and what's the test you applied to decide? Why did adapting the linter require a refactor rather than an import or a shell-out — i.e., what did `main()` withhold, and how does a pure `lint()` fix it? Which hyphen-resolution did you pick and what's the tradeoff? Cite the CORE-Bench 42%→95% story: what does it warn you about making a grader too rigid?*

### Milestone 3 — Per-dimension LLM judges with rubrics + "Unknown" hatch (60–75 min)
Subjective quality is what code can't reach. Three dimensions, three rubrics, three separate scores — never one blended number.
- **Deliverable — `evals/graders/judges.py`:** one judge per dimension: **voice-match** (does it sound like `voice/profile.md`), **SMYKM personalization** ("Show Me You Know Me" — is the personalization real and specific, not a mail-merge token), and **structure** (person-before-ask, one CTA, opener lands on *them*). Each judge: `model="claude-sonnet-4-6"`, `temperature=0.0`, a rubric with explicit `passing_description` / `failing_description`, and a mandatory **"Unknown" escape hatch** the judge must select when the draft is genuinely ambiguous (a judge forced to guess is a broken judge). Output JSON: `{reasoning, score: pass|fail|unknown, dimension, feedback}` — reasoning is required and comes *before* the score so it's not a post-hoc rationalization.
- **Do NOT import `cca-prep/shared/eval/*`.** It's a different repo, exam-grading only, and its `metrics.py` is aggregate-only — literally the anti-pattern you're avoiding. Borrow the dataclass *shape* as a pattern if you like; never wire it in.
- **Checkpoint 3:** *Why does each judge score one dimension instead of one judge scoring all three? Why must the "Unknown" hatch exist — connect it to why self-reported confidence is an invalid escalation trigger (CLAUDE.md). What breaks if reasoning comes after the score in the JSON?*

### Milestone 4 — Calibration loop to ≥80% judge-vs-Zo agreement (45–60 min)
A judge you haven't calibrated is a random number generator with good grammar.
- **Deliverable — `evals/calibrate.py`:** runs all judges over the ≥20 cases, compares each judge's verdict to *your* label from `decisions.log`/case frontmatter, and prints **per-dimension agreement %** (not one aggregate). Where a judge disagrees, print the case + the judge's reasoning side-by-side with your label. Read those transcripts — the disagreements are the signal. Tune the *rubric wording* (not the labels) until each dimension hits **≥80%**. If a dimension sits near 0%, suspect the grader, not yourself (the "0% pass@100" rule).
- **Scope honestly:** at 20 cases, one disagreement moves a dimension by 5 points, so ≥80% is 4-or-fewer misses on that dimension — reachable, but rarely on the first pass for all three at once. Budget for **one or two rubric-edit rounds per dimension**, and expect to spend your time on the one or two stubborn dimensions (usually SMYKM), not all three equally. If a dimension is still stuck after two honest rubric edits, do **not** relabel your cases to force the number — record the residual gap and your hypothesis in `NOTES.md` (a documented 75% beats a faked 80%). The time box covers the loop; a genuinely mislabeled case you discover while reading transcripts is a fine reason to fix *that label* (you were wrong), but never to fit the metric.
- **Checkpoint 4:** *Paste your before/after per-dimension agreement numbers. Pick one disagreement you resolved by editing the rubric — what was ambiguous, and what words fixed it? Why calibrate on a periodic pass rather than gating every run on human review?*

### Milestone 5 — Per-dimension report + two-model payoff run (45–60 min)
The whole point: a model swap becomes evidence, not faith.
- **Deliverable A — `evals/report.py`:** runs the full suite and emits a **per-dimension** table (voice-match / SMYKM / structure / deterministic), each with pass / fail / unknown counts and a rate. **No single headline accuracy number** stands alone (anti-pattern #10). State the reliability metric you chose and *why*: cold-outreach drafts are customer-facing and must be consistent, so **pass^k**, not pass@k — and show the math (e.g., 75% single-trial → 0.75³ ≈ 42% over 3 consecutive drafts).
- **Deliverable B — payoff run:** run the same suite against **two models** (`claude-sonnet-4-6` vs `claude-sonnet-5`), diff the per-dimension tables, **read the transcripts of the cases where they differ**, and write a one-paragraph pick-with-evidence in `NOTES.md`. Include a cost line with the *correct current* rates so the choice is economic, not just quality: **Sonnet 4-6 is $3/$15 per M; Sonnet 5 is on intro pricing at $2/$10 per M through Aug 31 2026** (from the reference card, live today). The newer model is currently the cheaper one — so if Sonnet 5 ties or wins on quality, the pick is unambiguous, and if the older model wins on quality you're paying *more* for that win. Do not paper over the gap by quoting one price for both; the direction of the cost difference is exactly what makes this an economic decision instead of a vibes one.
- **Checkpoint 5:** *Which model won and on which dimension — and did the cheaper/older one lose on quality or just tie? What's the one case whose transcript changed your mind? If both models scored identically, is your suite too easy — how would you know?*
