# A5 — The Machine

**"One command, tens of drafts, a cost ledger, and a kill switch that doesn't lose work."**

Hand-build the orchestrator-workers pipeline sales-machine's CLAUDE.md keeps implying: `signal-watch → shortlist → enrichment → voice-pack drafting → judges → outbox`, with the coordinator managing every worker, checking a token budget after every call and halting cleanly before it blows past (a best-effort control it interprets, not a hard code-enforced ceiling — see the determinism caveat in Milestone 1), checkpointing to disk so a kill mid-run resumes without repeating work, and treating worker failures as structured `isError` results it *decides* about — retry, skip, or abort — never swallows. This is the capstone: every prior layer (A1's loop, A2's gates, A3's tools, A4's judges) is a component the orchestrator calls. That cumulative dependency is the whole point — and the reason Milestone 1 is a reckoning, not a warm-up.

> **Meta-rule — you type every line.** Claude Code is a reviewer and explainer here, never a source. Ask it *why* a checkpoint scheme loses work on resume; never paste an orchestrator it wrote. Every checkpoint below is answered in your own words in `work/machine/NOTES.md`. The done-criteria turn on a live kill/resume you run and a ledger you reconcile by hand — copy-paste can't fake either.

## Execution model — read this first (this is not a Node program)
A `*.workflow.js` file in this repo is **not** a runnable Node script and there is no runtime to build. It is a **conversational orchestration DSL that Claude Code interprets** — Claude Code *is* the runtime. The globals the DSL uses (`meta`, `phase()`, `agent(prompt, opts)`, `parallel([...])`, `log()`, `StructuredOutput`, plus top-level `await`/`return`) are directives Claude Code reads and acts on: each `agent(...)` becomes a real sub-agent call Claude Code dispatches at the named model tier, `parallel([...])` fans those calls out, `schema` forces structured JSON on the return, and `return {...}` ends the run. `node scripts/backfill-icp.workflow.js` **throws** (`SyntaxError: Illegal return statement`, undefined `agent`/`parallel`/`phase`) — that is expected; it has never run as an OS process and is not meant to. There is no `package.json`, no `node_modules`, no binary. Concretely, throughout this spec:
- **"Run the machine"** = open `scripts/run-machine.workflow.js` in Claude Code and tell it to execute the workflow — it interprets your DSL top to bottom, dispatching the `agent()` calls you wrote.
- **"Kill mid-run" / "Ctrl-C"** = interrupt Claude Code mid-execution (Esc / interrupt) after some accounts have been processed but before the run returns.
- **"Re-run" / "resume"** = invoke the same workflow again; the on-disk checkpoints (Milestone 3) make the second interpretation skip accounts already past a stage. Resume is a property of *your* file-state logic, not of any harness — that is exactly what you're building.
- **The ledger's tokens/dollars** come from the per-call usage Claude Code reports for each interpreted `agent()` call (recorded into the `ledger` object as the run proceeds, reconciled by hand against the reference-card pricing). You are not writing a token meter; you are recording what the interpreter reports.

Because the runtime already exists (Claude Code) and was demonstrated by the reference file below, the per-milestone time estimates cover only the **pipeline-specific DSL you author** — the budget-halt, the checkpoint/skip logic, the error triage, the gate wiring — not the construction of an agent-execution engine.

> **Time-budget honesty — this is the tightest square in the whole program.** The brief gives A5 **two days (Days 11–12)** — one fewer than A3 (single MCP server, 3 days) or A4 (eval harness, 3 days) — yet A5 has strictly *more* net-new mechanics than either, and three of them are **precedent-free**: the reference file (`backfill-icp.workflow.js`) demonstrates `meta`/`agent`/`parallel`/waves and the gate-then-fanout shape, but it contains **zero** checkpointing, budget-ledger enforcement, or `isError` triage — grep it and you'll see. Milestones 3–4 ask you to invent those from the one-paragraph wiki descriptions alone. Budget accordingly: the per-milestone estimates below (they sum to **~3.75–5.0 hrs** of authoring: 45–60 + 45–60 + 60–75 + 45–60 + 30–45 min) are **typing time only** and deliberately exclude (a) real wall-clock of dispatching multiple live sub-agent waves per demo run, (b) debugging a non-deterministic interpreted DSL where a failure surfaces as "re-run and read the checkpoint files by hand," not a stack trace, and (c) the **2–3 separate live runs** the done-criteria require — one clean end-to-end, one kill/resume, one budget-halt, one deliberately-broken-worker triage. Realistically the two days are mostly consumed by those live runs and the debugging between them, not by the typing. If you're time-boxed, ship Milestones 1–3 solid (the checkpoint/resume is the interview story) and treat M4's error-triage breadth and M5's stretch as the cut line — don't fake a live run to hit the estimate.

### Milestone 1 — The dependency contract + run skeleton + ledger scaffold (45–60 min)
Before a single worker runs, decide what the machine is even allowed to call. The prior layers are partly missing; pretending otherwise is how you build a demo that lies.
- **Deliverable A — `work/machine/DEPENDENCIES.md`:** a table with one row per stage (`signal-watch`, `shortlist`, `enrichment`, `drafting`, `judges`, `outbox-gate`). Each row: *real artifact it should call* · *does it exist today (Y/N)* · *degraded-mode stand-in if N*. Your defaults, chosen deliberately and defended in `NOTES.md`: signal-watch → A3 MCP if present, else read a static `work/machine/fixtures/signals.json` you hand-author from `CLAUDE.md`'s product paragraph (685 signals / 36 categories is real); outbox-gate → A2's `lint-draft.py` if present, else a minimal inline deterministic check (≤100 words, one CTA, zero `voice/prohibitions.md` terms) the orchestrator runs *before* writing to `outbox/`; judges → A4's `evals/graders/*` if present, else a single Sonnet voice-match judge with an "Unknown" hatch. Rule: a degraded stand-in must be small and same-shaped so the real layer can replace it without touching orchestrator code.
- **Deliverable B — `scripts/run-machine.workflow.js` skeleton:** the `meta = {name, description, phases}` header naming all six phases with their model tier; the `SAFETY` constant (no git, external tools read-only, path-scoped writes under the repo, never print keys — copy the A2 rules verbatim from `CLAUDE.md`); a `BUDGET` constant (a token or dollar ceiling the coordinator checks after every call — see the determinism caveat below); a `CAP` constant — **pick a concrete integer** for the tens-per-week ceiling and write it into the file (e.g. `const CAP = 20;`), because "tens-per-week" is a qualitative phrase in `CLAUDE.md`, not a documented number; you are declaring the ground truth the run is checked against, so state your chosen value and defend it in `NOTES.md`; and a `ledger` object that every `agent()` call appends to (`{stage, label, model, in_tokens, out_tokens, usd}`). No workers yet — just the frame, the budget, the cap, and the ledger plumbing.
> **Determinism caveat — read before you write `BUDGET`.** `BUDGET`, `CAP`, and the checkpoint-skip logic are all directives *Claude Code interprets* — they live inside a model-interpreted DSL, so they are **best-effort controls the coordinator checks and honors**, not hard code-enforced guarantees. That is a real distinction this curriculum tests (the #1 concept: programmatic enforcement vs. prompt-based guidance, anti-pattern #3). Do **not** write or narrate `BUDGET` as "a ceiling it can't exceed" — write it as "the running total the coordinator checks after every call and halts on." The one genuinely deterministic gate in this whole pipeline is `lint-draft.py` in Milestone 4, which the orchestrator *shells out to* — real code with an exit-code contract, not a model deciding to comply. Hold that contrast; Checkpoint 4 makes you name it.

### Milestone 2 — Gate-then-fanout: signal-watch → shortlist (45–60 min)
Never fan out before you know the input is worth fanning out on. This is the single most reusable shape in the house DSL — one cheap probe, one quality gate, abort clean on failure.
- **Deliverable — the first two phases in `run-machine.workflow.js`:** `signal-watch` (a Sonnet — or Haiku, if summarizing a fixture — worker that pulls raw signals for a candidate account set and returns them via `schema`-forced JSON); then an **Opus `shortlist` gate** that scores ICP fit against `playbook/` + `voice/`, ranks, and returns *at most* `CAP` accounts — the concrete integer you declared in M1, not the vague phrase "tens-per-week" (`{shortlist: [...], dropped_reason: {...}}`). If the gate returns zero qualified accounts, `return {aborted, reason}` — do not draft to nobody. The cap is checked here, in the coordinator, not left to the drafting workers (and, like `BUDGET`, it's a control the interpreter honors — best-effort, not code-enforced; that's what Checkpoint 4 makes you name).
- **Checkpoint 2:** *Why gate before fan-out instead of drafting everything and filtering after? Put a token number on it — roughly what does one probe + one Opus gate cost vs. fanning out N drafting workers on an unqualified list (use the reference-card pricing)? Why does the shortlist cap live in the orchestrator and not in each worker's prompt?*

### Milestone 3 — Enrichment + drafting fan-out, with budget + checkpointing (60–75 min)
Now the expensive part — and the two things that make it production instead of a script: a budget the coordinator checks after every call and halts on, and disk state that survives a kill. (Both are best-effort controls the interpreter honors, not hard code-enforced guarantees — the determinism caveat in Milestone 1 is load-bearing here; Checkpoint 4 makes you reconcile it.)
- **Deliverable A — parallel enrichment + drafting:** for each shortlisted account, a worker enriches (warm-angle / persona, degraded-mode if A3 absent) and a worker drafts against the full `voice/` pack (profile → prohibitions → anchors), each with explicit objective + output format + tool boundaries in its prompt (vague delegation → duplicate work, per orchestration-patterns.md). Run in **sequenced waves** (`waves = [[...],[...]]`) like the reference file, not one giant `parallel()`, to spread quota.
- **Deliverable B — file-based checkpointing:** before each wave, and after each worker returns, write per-account state to `work/machine/run-<ts>/<account-slug>.json` (`{stage, status: pending|enriched|drafted|gated|written|failed, draft_path, tokens}`). On startup the orchestrator reads the run dir and **skips any account already past a stage** — and **emits a `log()` line per skip** (`skipping <account>: already <status>`), because Checkpoint 3 and the done-criteria ask you to paste exactly those lines as resume proof; a silent skip is unverifiable. So a `Ctrl-C` mid-wave and a re-run resume without repeating completed work, visibly. This is structured-note-taking-to-disk (context-engineering.md), your chosen long-horizon tactic.
- **Deliverable C — budget enforcement:** after every `agent()` call, add its usage to `ledger` and check the running total against `BUDGET`. On breach, stop dispatching new workers, flush checkpoints, and `return {halted: 'budget', spent, remaining_accounts}` — a clean stop that loses nothing, not a crash. The iteration/wave count is only a *safety net* (anti-pattern #2); the budget is the primary control.
- **Checkpoint 3:** *Kill the run mid-wave, then re-run it. Paste the two log lines proving the second run skipped the already-drafted accounts. Which of context-engineering.md's three long-horizon tactics did you implement, and why not the other two here? What exactly would be lost if you checkpointed only between waves instead of after each worker?*

### Milestone 4 — Error propagation + the outbox gate (45–60 min)
A worker failing is normal. The orchestrator *deciding* what to do about it — retry, skip, abort — is what separates this from a script that returns `[]` and calls it success (anti-pattern #7).
- **Deliverable A — structured error triage:** workers return failures as `{isError: true, errorCategory, isRetryable, detail}` (anti-pattern #6 — never a bare `null`/empty). The orchestrator branches on the fields: `isRetryable` transient (rate-limit/timeout) → retry once with backoff; a hard content failure (draft won't pass the gate after one repair) → skip that account, log it, continue the rest; a `SAFETY`/auth breach → abort the whole run. Record every decision in the ledger/log — a skipped account is a visible line, never a silent drop.
- **Deliverable B — the A2 gate on the way into `outbox/`:** every draft passes the outbox-gate (A2's `lint-draft.py` or your M1 inline stand-in) **before** it is written to `outbox/YYYY-MM-DD-company-touch.md`. A gate failure is not a warning — the draft does not land, the account is marked `failed` with the reason, and (optionally) one repair worker gets a single attempt. If A4 judges exist, run them inline here too, per-dimension, and attach scores to the draft frontmatter. This is the brief's "A2 gates enforce on the way in" made literal.
- **Checkpoint 4:** *Walk one worker error all the way up: what did the worker return, how did the orchestrator classify it, and what did it decide — quote the three `isError` fields. Why is "skip and log" correct for a failed draft but "abort" correct for a SAFETY breach? What would anti-pattern #7 look like here specifically — write the two lines of code you deliberately did NOT write.*
- **Checkpoint 4b (the enforcement seam — the reconciliation this whole capstone turns on):** *Sort A5's three controls into two piles. Which is **real code-enforced** (deterministic, cannot be talked out of) and which are **soft, model-interpreted** (the coordinator chooses to honor them)? — the outbox `lint-draft.py` gate, the `BUDGET` halt, the checkpoint-skip/resume. Then: your budget lives inside a Claude-Code-interpreted DSL, so a run that ignores it isn't a crash, it's the model not complying — is a "budget it can't exceed" living there actually a guarantee in the A2 sense, or is it precisely anti-pattern #3 (prompt-based enforcement of a critical rule)? What would a **truly hard** ceiling require instead — an out-of-band process kill, a real harness metering tokens, a wrapper that SIGKILLs at $N — and why couldn't the interpreted DSL alone give you that? This is the A2 lesson ("move rules from prompt to physics") applied to your own capstone: name honestly which of your controls are physics and which are still prompt.*

### Milestone 5 — Cost ledger, workflow-vs-agent writeup, live demo (30–45 min)
The payoff is a number you paid and a decision you can defend.
- **Deliverable A — `work/machine/run-<ts>/ledger.md`:** the run's cost ledger — a per-stage table (`stage | model | calls | in/out tokens | $`) with a total, emitted by a final Haiku summarizer or written directly from the `ledger` object. Then in `NOTES.md`: state the **multi-agent tax you actually paid** for this run and whether it was justified — tie it to the ~15x/90.2% economics (loosely-coupled, parallelizable → orchestrator-workers earns its keep; if your stages turned out tightly coupled, say a single agent would've been cheaper and why).
- **Deliverable B — the append to `wiki/log.md`:** one line, newest-first, matching the file's actual house format — `YYYY-MM-DD <category>: <description>` with a plain space after the date, no em-dash (check the existing entries before you write yours): `YYYY-MM-DD run-machine: N accounts shortlisted, M drafts written, $X spent, K skipped`.
- **Deliverable C — the live demo:** run the machine end-to-end once, then run it again after a mid-run kill to show the resume. This is the interview story — the kill switch that doesn't lose work.
- **Checkpoint 5:** *What did this run cost, and was multi-agent the right call for it — argue it from your ledger, not the blog. If you rebuilt this as a single long-running agent instead of an orchestrator + workers, what would get cheaper and what would get worse? Point to the one stage that most justifies the orchestrator-workers overhead.*
